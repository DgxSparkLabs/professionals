# B1. Runtime joins: assignment, session, run, attempt, exchanges

Spike for the audit (docs/spec/audit.md), step B1. Question: from what `pros` and Claude Code already write, can a task message (assignment) be joined to the Claude session and run that handled it, to each delivery attempt, and to the model exchanges it caused, and with what confidence?

Method:
- `research/audit_reader.py`, a stdlib reference reader. Run on the step A fixtures and, read-only, on one operator's local store (a frozen copy, read 2026-11-12 16:05 UTC; only counts are reported here).
- `research/b1_probe.py`, one controlled live run with the stub claude (about 13 s). Its scenario: a stop-hook delivery, a killed hook followed by a redelivery marked dup, two tasks in flight at once, then resume and fork.
- `tests/test_audit_research.py` pins the rules below.

## Results

### 1. Message → root task (parent walk)

- Fixture `ask_delegation`: the child `m-…05` (task `t-…01`) walks to the root `m-…01` (task `fx-root`) at depth 1, with no broken links.
- Real store: 110 task messages, parent set on 115 of 222 messages (tasks and replies), maximum chain length 2.
- Task-id strings are not joinable. The child gets a new task id, which confirms plan decision 3.
- **Settled:** an assignment is a message id, and the root is found by walking `parent`. A missing parent is shown as a broken link and is never guessed (the reader returns `broken_parent`).

### 2. Message → Claude session: the transcript header is the verified link

Real transcripts (2.1.322; the store's 110 delivered tasks were looked up across every local transcript):

| Delivery path (`via` in the record) | Tasks | Header row found | Row shape |
|---|---|---|---|
| paste | 86 | 86 (85 in one file, 1 in two files) | `type=user`, string content. The header is at offset 0 or right after a `<pasted_content id=…>` wrapper |
| stop-hook | 24 | 24 | `type=user`, `isMeta=true`, string starting `Stop hook feedback:\n[pro-msg id=…`. Each is accompanied by an `attachment` row (`hook_blocking_error`, Stop) and a `system/stop_hook_summary` row |

**Unknown A6 settled:** a stop-hook delivery does reach the transcript with its header (24 of 24). Both delivery paths therefore get a *verified* join.

The header string also appears in rows that are not deliveries, and these must never count as joins:

- `tool_result` content: the output of `pros inbox` or `pros wait` (47 rows).
- `api-request-blob` rows (174 rows).
- `last-prompt` rows (830 rows).
- Two human-typed prompts that quote a header mid-text.

The reader's rule: a `type=user` row whose text (a string, or text-only blocks) matches `^(Stop hook feedback:\n|<pasted_content…>\n)?\[pro-msg id=`. The test `test_header_rules` covers each excluded shape.

### 3. Message → session by history time window (the fallback)

Real store, 110 injected tasks:

| Join | Count | Note |
|---|---|---|
| History run window of the recipient covers `injected_at` | 94 (one run each) | All 94 confirmed by the header in that run's transcript |
| No history run covers it | 16 | Delivered before history rows existed. Header rows exist in transcripts of sessions unknown to history |

Stub probe (`b1_probe.py`, the tasks in order):

| Task | Path | Record | Stub deliveries | Window runs | Confidence |
|---|---|---|---|---|---|
| b1-first | paste | answered | 1 | S1 | mapped |
| b1-second | stop-hook | answered | 1 | S1 | mapped |
| b1-busy (no reply) | paste | failed (no `failed_at`) | 1 | S1 | mapped |
| b1-dup | stop-hook | answered, `dup=true`, attempts 0 | 1 (marked dup) | S1 | mapped |
| b1-resumed | paste | answered | 1 | S1+S2 | unassigned |
| b1-forked | paste | answered | 1 | S1+S2 | unassigned |

Runs from history: S1 fresh, S1 resume (same Claude id), S2 fork. The state file (`run/state/<session>.json`) ends holding only S2. It is overwritten on every hook, so it cannot place earlier messages.

- **Finding:** the time windows of runs that start and stop within a second overlap, so a task right after a resume or fork matches two runs. Windows are not a sound join. They only identify the session when exactly one run covers the time.
- **Settled for C/D1:** the emitter must stamp the run on the delivery event. At `mark_injected`, emit `{msg id, via, tmux session, Claude session id from the state file, local run id}`, with the run id minted at spawn (plan decision 6). A transcript header then upgrades the join to *verified*.

### 4. Attempts: redelivery vs re-execution

- A killed stop hook (exit −9) followed by recovery gave one message with `dup=true`. The stub saw exactly one delivery, because the killed hook died before printing. `attempts` stayed 0 (it counts paste failures only).
- The record cannot tell whether the first claim reached the session. Only the count of transcript header rows can: 1 header means one delivery, 2 headers for the same id in one session means a real duplicate delivery.
- Real store: 1 message with `dup=true`. No message has two header rows in one session file. The one id seen in two files is a copied transcript, not a redelivery.
- A genuine re-execution is a new message (new id). Same task id, same body and same target are refused as `duplicate` by `do_send` (T042), so they never create a second assignment.
- **Settled:** an attempt is one observed delivery, meaning one header row per session or one inject event. `dup` is evidence ("possibly delivered twice"), not a count. Restart re-sends (B10 gap) appear as extra inject events on the same message id.

### 5. Overlapping tasks and manual turns

- Real store: 0 of 110 deliveries arrived while another task to the same session was still unanswered.
- Stub: 3 of 6 overlapped. b1-busy never replied and stayed in flight in the records until it failed at stop. The failure time is not stored (no `failed_at`), so its in-flight interval has no recorded end.
- Real professional transcripts hold 2 plain prompts (human-typed, for example through `pros attach`) and 94 header prompts. Usage after a plain prompt is session-only.
- **Settled:** exchanges after a verified header belong to that message until the next plain prompt. If another assignment to the same session is in flight at that moment, the exchange is marked *overlap* and reported, not split. A `failed_at` (or a fail event) is required from D1.

### 6. Usage attribution coverage (feeds B2)

- Fixture: root own 140, child own 80, inclusive 220, root session-only 30, fork copy 0. All exact.
- Real store: 889 unique exchanges, 176,424,882 tokens. 175,601,223 (99.53 %) follow a verified header. 823,659 (0.47 %) follow the 2 manual prompts (session-only).

## Join-confidence policy (proposed for C)

| Level | Rule |
|---|---|
| verified | A delivery header row in the transcript of the session the delivery event (or history) names |
| mapped | No transcript row, and exactly one run of the recipient covers `injected_at`, or the inject event carries the run id |
| unassigned | Otherwise. Usage stays at session/run level and is counted in the residual |

## Unresolved

- With the stub, header rows are not written, so the stub run proves the record side only. Header shapes come from real 2.1.322 transcripts. Other Claude Code versions are unverified: run `audit_reader.py --counts-only` per version.
- Real resume and fork transcripts were not available locally, because all 45 history runs are fresh. Whether a real `--resume` rewrites earlier rows into the same file, and whether `--fork-session` copies them with the same `message.id`/`requestId`, is still unverified on real data. The fixture models a fork copy, and the reader's first-wins rule (earliest file first) handles both.
- Messages lack `failed_at` and a per-attempt log. Only new emitter events (D1) can supply them.
