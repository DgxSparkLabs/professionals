# B3. First-release metric catalog and rubric fixtures

Spike for the audit (docs/spec/audit.md), step B3. It defines the five first-release cards (brief §4) with every field the brief requires. It also adds rubric and evaluation fixtures, and golden values on the step A fixture:

- `research/metrics_ref.py`: the reference computation.
- `tests/fixtures/audit/rubrics/`: two rubrics and three evaluations.
- `tests/fixtures/audit/golden/cards.json`: the golden values.
- `tests/test_audit_research.py`: checks the golden file and asserts the key numbers literally.

## Common rules (every card)

- **Window and event time.** Each card names the timestamp that places a record in the window (below). `cutoff` is the end of the window, or the query time if that is earlier. It is shown on every card.
- **Unit.** Root tasks and child assignments are always counted apart (brief §4). A root task is a message with no `parent`. A child assignment is a message with a `parent`, linked by message id (B1).
- **Ratios** are shown as `[numerator, denominator]`, never as a bare percentage. When the denominator is 0, the ratio is `null` with a reason.
- **Coverage and source quality** are shown on every card: how many records had the needed field, which source supplied it (emitter event, backfilled record, transcript, session counter), and join confidence (B1 levels).
- **Dimensions** (where available): professional, revision, model, task class, direct (sent by the user) vs delegated (`parent` set), scope.
- **Pairs.** A card is never shown without its partner: pass rate with coverage, speed with sample size, tokens with unavailable share. Activity volume is never a ranking.

## The five cards

### 1. Assigned work

| Field | Definition |
|---|---|
| Question | How much work did professionals receive? |
| Numerator | distinct assignment ids (`kind=task` messages), split into root tasks and child assignments |
| Denominator | — (count) |
| Unit / cohort | assignment. Cohort = recipient professional (+ revision) |
| Event time | assignment `created` in the window |
| Exclusions | `duplicate` sends refused by T042 (no message exists); notes and replies |
| Coverage / quality | records from emitter events; backfill marked with provenance before the cutoff |
| Decision | which professionals get real work |
| Golden (fixture) | 2 assignments = 1 root + 1 child |

### 2. Evaluation coverage and pass rate

| Field | Definition |
|---|---|
| Question | Of the finished work, how much was judged, and how much of that passed? |
| Eligible | completed tasks: delivery state `answered`, late answers included. Root tasks and child assignments on separate rows |
| Effective verdict | latest non-superseded evaluation per target. An operator outranks an automated check on the same target. Every evaluation stays visible |
| Conclusive | `passed`, `partial`, `failed`. Not conclusive: `inconclusive`, `unreviewed` (no evaluation) |
| Coverage | conclusive ÷ completed eligible |
| Pass rate | passed ÷ conclusive. The counts of partial, failed, inconclusive and unreviewed are always shown beside it |
| Event time | completion (`answered_at`) in the window. The verdict's `effective_at` ≤ cutoff |
| Exclusions | assignments not completed (failed, cancelled, still in flight) are outside the denominator and shown as a count |
| Decision | is the professional effective for this kind of work |
| Golden | root: coverage [1,1], pass rate [0,1], partial 1 (e3 supersedes e2; criterion C1 failed). Child: coverage [1,1], pass rate [1,1] (e1, automated) |

Rubric rule (fixture `rubric_architecture_review.json`):

- **passed:** every required criterion passed.
- **failed:** every required criterion failed.
- **partial:** otherwise.
- **inconclusive:** any required criterion has no outcome.

A stored status that contradicts its own criteria is a validation error for D4.

### 3. Deadline miss rate

| Field | Definition |
|---|---|
| Question | How often is work not answered by its deadline? |
| Eligible | assignments whose `deadline` ≤ cutoff, cancellations excluded (and counted) |
| Missed | no `answered_at` ≤ `deadline`. A late answer **is** a miss and is also counted as `late_answers_among_missed` |
| Rate | missed ÷ eligible. Root and child shown apart |
| Event time | `deadline` in the window. `not_yet_due` is shown |
| Rule | computed from `deadline` vs `answered_at`. The runtime `overdue` flag is set only when some pump runs, so it is evidence, not the event |
| Decision | routing and deadline sizing |
| Golden | all [1,2], root [1,1] with 1 late answer, child [0,1] |

### 4. Queue and work duration

| Field | Definition |
|---|---|
| Queue time | first observed delivery (`injected_at`, later the first inject event) − `created` |
| Reply latency | `answered_at` − first delivery |
| Active time | sum of known model/tool spans. **Not available in the first release from records alone.** Shown as n=0 with coverage, never inferred from latency |
| Statistic | p50 and p95, nearest rank. n and coverage `[n, eligible]` beside each percentile |
| Time base | UTC wall times from records. Monotonic durations only where one process measured both ends |
| Decision | is the bottleneck queueing, the professional, or execution |
| Golden | queue p50 0.38 s, p95 0.39 s (n 2/2). Reply latency p50 0.09 s, p95 40.69 s (n 2/2). Active n 0/2 |

### 5. Accounted tokens

| Field | Definition |
|---|---|
| Sum | unique exchanges (dedup B2) in the window: input / output / cache write / cache read, never one blended number without the split |
| Split | linked task usage (verified or mapped join, own and inclusive per root), session-only usage, and unavailable usage (session counter minus transcript sum, B2) |
| Event time | exchange `timestamp` |
| Scope rule | two surfaces compare totals only at the same scope (assignment own, root inclusive, session) |
| Quality | provider counts, derived cost from the pinned table, unpriced share. Join confidence per row |
| Decision | which revisions and context sources drive cost |
| Golden | 250 unique = 220 linked (root own 140 + child 80, inclusive 220) + 30 session-only. Unavailable `null` (the fixture has no session counter) |

## Waiter outcomes (not a card; needed for the trace)

The fixture's caller saw `ask --wait 2` → exit 3 (pending), then `wait` → 5 and 5. The late reply was shadowed by the timeout note (known gap T-X1). Waits are stored as their own records `(caller, task, start, end, outcome, exit)` and never change the assignment's delivery or deadline status.

## Ideas tested against the decision they support (brief §8.2)

- **Conversion funnel** (assigned → delivered → answered → evaluated → passed). It supports "where work is lost". It could mislead because evaluation is optional: a low evaluated step is a coverage problem, not a quality one. So the funnel always shows coverage, and it is a later card.
- **Control chart on reply latency.** It supports "did a release shift latency". It could mislead because latency is dominated by task mix (one 40 s root among 0.1 s children in the fixture). So it is only drawn within one task class, and it is a later card.

## Unresolved

- Task class is not recorded anywhere today. Cards group by it only once an assignment carries a class (an operator tag or a rubric choice).
- Active model/tool time needs span events (D1) or transcript timestamps per exchange. The latter only gives wall time between rows, so whether that counts as "active" must be decided in C.
- Eligibility for adoption metrics (later lenses) is not defined. No eligibility events exist yet.
