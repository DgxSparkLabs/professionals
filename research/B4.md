# B4. Storage and access: SQLite WAL, spool, recovery, overhead, permissions

Spike for the audit (docs/spec/audit.md), step B4. The measurements come from `tests/bench_audit.py`, which is stdlib and is not part of the unittest discover pattern:

- Run: `python3 tests/bench_audit.py --dir <dir on the PRO_HOME file system>`.
- Host: 12 CPUs, Linux, ext4. Python 3.14.4, SQLite 3.46.1.
- A first run on tmpfs gave the same numbers except for fsync (noted below).

## Results (ext4)

| Measurement | Result |
|---|---|
| Emit one event (open O_APPEND 0600, one `write`, close), 10,000 events | p50 0.011 ms, p95 0.020 ms, max 0.094 ms; 241.7 bytes/event |
| Same with `fsync` per event, 2,000 events | p50 1.68 ms, **p95 4.96 ms**, max 20.3 ms (tmpfs: p95 0.017 ms) |
| One `pros version` process (the floor every transition already pays) | p50 73.0 ms, p95 81.1 ms |
| 4 writer processes + 2 readers, 1 event per transaction, 200 each | 800/800 rows; commit p50 0.034 ms, p95 2.77 ms, max 43 ms; 0 busy retries (busy timeout 5 s); integrity ok |
| Same, 100 events per transaction, 50 each | 20,000/20,000 rows; commit p50 0.67 ms, p95 1.68 ms, max 255 ms; 0 busy retries |
| Snapshot consistency: a reader counts twice inside one read transaction while writers commit | 0 mismatches in 2 × ~1,400 read transactions |
| Checkpoint while a reader holds a snapshot, 10,000 events | WAL grows to 34.95 MB; `wal_checkpoint(TRUNCATE)` returns busy (1, 8,484 frames, 7 checkpointed) |
| Checkpoint after the reader ends | complete, WAL 0 bytes, 204 ms |
| Writer SIGKILLed inside an open transaction | only the committed row survives; `integrity_check` ok |
| Spool writer killed mid-line | 1 complete line read, the partial line is skipped (no trailing newline = not yet written) |
| Spool at a file-size limit (stands in for a full disk) | 15 events written, then errno 27 (EFBIG) ×84 and 28 (ENOSPC) ×1; **the file ends in a torn line** |
| Store size, 10,000 events with 2 indexes, after VACUUM | 2.84 MB = 283.9 bytes/event |
| Import throughput (one transaction, `INSERT`) | ~385,000 events/s. A re-import of the same 10,000 with `INSERT OR IGNORE` on the event id: 10,000 rows, 0.012 s |
| Modes under umask 022 | dir created 0700 (after chmod), db pre-created 0600 → `-wal` and `-shm` are also 0600. **A db created by sqlite itself is 0644 and so is its WAL** |

## What this settles for C

1. **Emit cost is negligible.** Without fsync it is 0.020 ms p95: under 0.03 % of the 73 ms a `pros` process already costs, and far inside the 5 ms budget (FR-001, SC-002). **No fsync per event.** Fsync alone reaches p95 4.96 ms on ext4, which uses up the whole budget. A crash of `pros` loses nothing that `write()` returned for. Only an OS crash can lose the last seconds.
2. **One spool file per process, one `write()` per event.** After any write error the emitter sets the degraded flag and stops appending to that file. A torn last line cannot be followed by a valid event, because appending after it would merge two events. The importer:
   - skips a line without a trailing newline and re-reads it later;
   - counts an unparseable complete line as a coverage gap, never as a crash.
3. **SQLite WAL with one importer is enough.** Even 4 concurrent writers had 0 busy retries with a 5 s busy timeout. The design keeps a single importer anyway (plan decision 1), so hooks never wait on a lock. Settings: `journal_mode=WAL`, `synchronous=NORMAL`, `busy_timeout`, batches of about 100 events per transaction, idempotent on the event id.
4. **Readers must not hold transactions open.** One long snapshot blocked checkpointing and grew the WAL to 35 MB for 10,000 events. Rules:
   - Query API calls use one short read transaction each.
   - The snapshot id (plan decision 10) is `(schema version, last import batch, max seq)`, not a held transaction.
   - The dashboard re-queries; it does not hold a cursor.
   - The importer runs `wal_checkpoint(TRUNCATE)` after a drain.
5. **Crash recovery comes from SQLite plus the idempotent import.** An uncommitted batch is rolled back. The spool cursor advances only after commit, so a re-read is ignored by the event-id key. This shape is ready for the D1 test (SC-003).
6. **Disk use.** About 240 B per spooled event plus about 285 B per stored event. 100,000 events a month comes to about 52 MB before retention. The spool is deleted (or truncated) after a confirmed import.
7. **SQLite feature floor.** No `RETURNING` (3.35), no `STRICT` (3.37), no reliance on JSON functions (built in only from 3.38). UPSERT (3.24) and window functions (3.25) are fine. Python 3.9 was not available on this host, so the floor is set by the documented versions.

## Access (FR-040) and the same-OS-user limitation

| Layer | Finding |
|---|---|
| File modes | Create `$PRO_HOME/audit/` with `mkdir` then `chmod 0700`. Create the db file 0600 **before** sqlite opens it (sqlite itself creates 0644 under umask 022). WAL/SHM inherit 0600. Open spool files with mode 0600. The existing `write_json` does not set modes: today's `run/msgs/*.json` are 0644 (T-X2) |
| Professional sessions | Add `audit/` to `pro_home_denies()`. The Read/Edit deny rules then cover it, and so does the sandbox `denyRead` when the sandbox is on |
| `pros` run by a professional | Professionals may run `Bash(pros *)`, so **any `pros audit …` read or management command must call `require_user`**. Otherwise a professional reads the audit through the CLI and bypasses the deny rules. The emitter inside a professional's own `pros` call only appends to the spool; it never reads |
| Sandbox | On this host the sandbox probe fails (nested user namespaces refused), so professionals run unsandboxed and the deny rules plus the narrow Bash allowlist are the only barrier. **Unverified:** with the sandbox on, whether a professional's `pros` call can still append to `$PRO_HOME/audit/spool/` (sandbox write scope). The same open question applies to `run/` today |
| Same OS user | Every professional runs as the operator's own user. 0600/0700 protects against other users, not against a process of the same user that is not bound by Claude Code permissions: a persona granted wider tools (`--mode` explicit), a manual shell, or another program. The owner can always read, edit or delete the store. This must be written down in the operations doc (G) and never presented as tamper-proofing. Corrections and deletions are audit events, but a same-user process can remove those too |

## Unresolved

- Behaviour with the sandbox on (see above). It needs a host where the sandbox probe passes.
- macOS: the file-mode and fsync costs were not measured (fsync there is `F_FULLFSYNC`, much slower). The no-fsync decision makes this moot for the emitter.
- A real disk-full test (ENOSPC on a small loop file system) needs root. The rlimit stand-in reproduces the torn-line case and both errnos.
- Importer behaviour under a spool backlog of 10⁶ events (memory, batch size) belongs to the D1 benchmark budget.
